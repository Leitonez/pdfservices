# Spec Delta

## Purpose

Guarantees that customer documents are never retained, that access records meet Brazilian legal retention rules, that the AGPL source-code offer is made to network users, and that every API error has one predictable shape.

## ADDED Requirements

### Requirement: Documents are never stored or logged
The HTML sent for conversion and the generated PDF SHALL exist only in memory during the request. They SHALL NOT be written to disk or a database, and SHALL NOT appear in logs, including messages from the conversion engine and error details. Everything logged or stored about a conversion SHALL be limited to metadata (sizes, duration, counts, account and key ids).

#### Scenario: Conversion failure log
- **WHEN** a conversion fails
- **THEN** the log records only the exception type, never the document content or the engine's message

### Requirement: Access log retention
The system SHALL record an access log entry for each successful login and each charged API call, with timestamp, event type, client IP (first address of `X-Forwarded-For`, or the connection address) and, for API calls, the key and transaction ids. Entries SHALL be kept for 183 days (Marco Civil da Internet, art. 15) and then removed automatically.

#### Scenario: Retention
- **WHEN** an access log entry is 183 days old
- **THEN** it is removed automatically

### Requirement: AGPL source-code offer
Every HTTP response produced by an API endpoint, success or error, SHALL include `X-Source-Code: https://github.com/Leitonez/pdfservices` and `X-License: AGPL-3.0-or-later`. Responses generated by the hosting platform before any endpoint runs (unknown routes, CORS preflight) are outside this requirement. Transactional e-mails and the website SHALL also link to the source code.

#### Scenario: Headers on any response
- **WHEN** a client calls any endpoint, including one that returns an error such as `POST /v1/html2pdf/xyz`
- **THEN** the response carries `X-Source-Code` and `X-License`

### Requirement: Browser clients can read billing headers
Every API response SHALL include `Access-Control-Expose-Headers` listing `X-Transaction-Id, X-Charged-Amount, X-Balance, X-Blocked-Resources, X-Source-Code, X-License`. Cross-origin browser access SHALL be allowed only from the website and panel origins.

#### Scenario: Panel reads the balance header
- **WHEN** the panel's test screen calls the conversion endpoint from the browser
- **THEN** it can read `X-Balance` from the response

### Requirement: Uniform error format
Every API error SHALL be a JSON body `{"error": "<code>", "message": "<text>", "fields": {...}}`, where `code` is a stable machine-readable identifier, `message` is in Brazilian Portuguese for display, and `fields` (omitted when empty) maps input fields to messages. JSON responses SHALL use camelCase property names, omit null properties and keep non-ASCII characters unescaped. A request aborted by the client SHALL end with status 499 and no body. Unexpected failures SHALL return 500 `internal_error` with a generic message. A malformed JSON body SHALL return 400 `invalid_json`, an empty one 400 `invalid_body`, and portal JSON bodies above 16 KB SHALL return 413 `payload_too_large`.

#### Scenario: Validation error shape
- **WHEN** a signup has an invalid CNPJ and e-mail
- **THEN** the response is 400 with `error: "validation_error"` and `fields` containing `cnpj` and `email`

#### Scenario: Unexpected failure
- **WHEN** the database fails unexpectedly
- **THEN** the response is 500 with `error: "internal_error"` and no internal details

### Requirement: Health endpoint
`GET /ping` SHALL respond 200 with the plain text `pong` without authentication. API routes SHALL have no `/api` prefix.

#### Scenario: Ping
- **WHEN** a monitor requests `GET /ping`
- **THEN** the response is 200 `pong`
